# Sentinel Dashboard Development Guide

## 1. Purpose

This guide explains how to install, run, inspect, and extend Sentinel Dashboard. The declared scripts and a verification attempt are documented below; the current baseline checks do not all pass.

## 2. Prerequisites

Install:

- Node.js compatible with the selected Next.js version.
- npm.
- Git.
- A code editor with JavaScript and JSX support.

Check versions:

```bash
node --version
npm --version
git --version
```

The team should establish and document a supported Node.js version after validating the framework's compatibility requirements.

## 3. Clone and Install

```bash
git clone https://github.com/prolificsidekicklabs/sentinel-dashboard.git
cd sentinel-dashboard
npm install
```

For reproducible CI builds, commit and use the lockfile generated by the approved package manager. Prefer `npm ci` in CI once the lockfile is present and validated.

## 4. Run Locally

```bash
npm run dev
```

Open `http://localhost:3000`.

Build and run the production application:

```bash
npm run build
npm run start
```

## 7. Data and Component Contracts

Current components accept JavaScript objects through props. For example, `PriceChart` expects a market-data object, while `AgentRoster` expects an array of agent opinion objects.

Before replacing simulated data with a provider:

1. Define canonical schemas.
2. Validate inputs at the application boundary.
3. Represent loading, empty, stale, and error states separately.
4. Ensure timestamps and units are explicit.
5. Reject invalid or incomplete market data.
6. Keep provider-specific response formats out of presentation components.
7. Add tests for valid and invalid inputs.

Do not treat a numeric value as a valid market price merely because it can be rendered.

## 8. Development Workflow

1. Create a branch from the current default branch.
2. Make one logically scoped change.
3. Add or update tests.
4. Run relevant checks.
5. Review the diff for security and data-integrity concerns.
6. Update documentation when behavior or contracts change.
7. Open a pull request.
8. Merge only after required reviews and checks pass.

Example:

```bash
git switch -c feature/market-state-contract
# Make changes
npm test
npm run build
git diff --check
git status
```

Run the checks supported by the actual repository configuration; do not assume a command passes because it is listed in the manifest.

## 9. Recommended Testing Layers

### Unit tests

Test pure transformations, schema validation, indicator calculations, and risk-policy functions.

### Component tests

Test rendering, empty states, invalid input handling, accessibility, and user interactions.

### Integration tests

Test the flow from a validated market snapshot through assessment display and decision rendering.

### End-to-end tests

Test core workflows in a browser, including loading, errors, stale data, keyboard navigation, and responsive layout.

### Safety tests

Verify that missing data, stale data, rejected assessments, denied authorization, and risk-limit breaches cannot be represented as approval.

## 10. Observed Code Issues

- `FocusMode` receives the expected `marketState` and `agents` fields, but always displays `data.agents[0]`; it does not select an agent dynamically.
- `FocusMode.jsx` and `EventRail.jsx` include a literal `$` immediately before a template interpolation in a `className` string. This is not a JavaScript syntax error, but the extra character is emitted in the class value.
- Verify all component props before accessing nested arrays or objects.
- Check that generated chart values and timestamps are labeled as synthetic in demo mode.
- Remove browser alerts from production command workflows.
- Review unused state and error-handling paths in the main page.
- Correct the invalid comment opener at the start of `next.config.js` before retrying the build.
- Align the Next.js, `eslint-config-next`, and ESLint versions; add and validate the missing lint, TypeScript, and test configuration before treating those checks as available.

These findings are documented, not fixed by this documentation-only change. See the verification table above for observed command failures.

## 11. Definition of Done

A change is complete when:

- Its intended behavior is documented.
- Inputs and outputs are validated.
- Tests cover normal and failure cases.
- No secrets or sensitive information are committed.
- Accessibility and responsive behavior are considered.
- Relevant checks have been run and results recorded.
- The pull request explains any unverified assumptions or follow-up work.
